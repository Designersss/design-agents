# AIMock — Профессиональные агенты из коробки: назначаем работу, не обучаем профессию

**Статус:** концепция для согласования. Код интерфейса `main` не изменяется до утверждения.  
**Источник:** утверждённая `AIMock_Agent_Professions_Specification_v0.6_APPROVED.pdf`, A.1–A.7 и C1–C6; ранее утверждённая архитектура v6.  
**Причина:** текущие универсальные настройки «Чем занимается агент», «Дополнительные условия» и «Когда передать разговор человеку» ошибочно вынуждают владельца писать собственный prompt и воспроизводить встроенные профессиональные навыки.

## Решение

Профессия создаётся из версионируемого **паспорта профессии**, независимо от workspace (personal/team). В нём неизменяемы профессиональная цель, алгоритм, формат результатов, безопасное общение, уточнения, достоверность, границы полномочий, реакции на отказ инструментов, эскалация, защита данных и ограничения профессии. Это не пользовательские поля, не editable system prompt, не переключатели.

Экземпляр агента хранит только **назначение профессионалу конкретной работы**: ссылки на бизнес-объекты (вакансии/товары/услуги/категории обращений/источники мониторинга), назначенные знания, разрешённые подключения и операции, адресатов результата, необходимые бизнес-критерии и операционные ограничения. Операционные данные должны иметь строгие поля, а не универсальные текстовые инструкции.

Исполнение = platform-owned policies + profession manifest + validated tenant bindings + operation context + structured, auditable output. Промпт не может повысить права. Нет дублирования одной настройки одновременно в Workspace, экземпляре агента и вакансии.

### Что делать с универсальными полями

| Было в UI | Решение | Где источник истины |
|---|---|---|
| «Чем занимается агент» | **Убрать из всех экземпляров** как универсальную текстовую инструкцию; заменить полями по профессии | Код профессии + привязанные бизнес-объекты |
| «Дополнительные условия задачи» | Убрать универсальное свободное поле; специальные проверяемые поля только там, где они действительно нужны | Профиль конкретной профессии / бизнес-объект |
| «Когда передать разговор человеку» | **Убрать как редактируемое правило**; условия безопасной и штатной передачи встроить; оставить только выбор ответственного и канала/очереди передачи | Platform-owned handoff engine + workspace access |
| «Настройка тона/языка/системных правил» | Не показывать: качество и этика профессии встроены | Паспорт профессии, регрессионные тесты |
| «AI-модель» | Автоматически или совместимая публичная модель; список идёт из Admin, не hardcode | Публикуемый модельный каталог |
| «Готовность к запуску» | Отдельная проверка, не настройка навыков и не блок обзора | Серверная validation/readiness |

## HR-рекрутер: что уже умеет

1. Принимает отклик только на доступную, разрешённую вакансию и фиксирует Application до начала интервью; защищённо выявляет дубли без раскрытия чужих данных.
2. Проводит одно связанное с заявкой интервью в одном подтверждённом канале. Генерирует вопросы из **актуальной версии конкретной вакансии** и недостаточно подтверждённых требований, а не из generic пользовательского prompt.
3. Запоминает ответы, связывает выводы с проверяемыми источниками и отмечает «подтверждено / не подтверждено / недостаточно данных». При противоречии уточняет; отсутствие сведений не выдаёт за отказ.
4. Формирует фактическую сводку и одну из двух **предварительных** очередей: «На рассмотрение» / «Потенциальный отказ». Никаких процентов соответствия и дискриминационных критериев.
5. Передаёт обе категории на решение владельцу/уполномоченному HR. **Никогда** сам не отправляет окончательный отказ, не меняет стадию внешней ATS без разрешённого действия человека, не рассылает резюме в уведомлениях.
6. Не навязывает напоминания молчащим кандидатам; не обещает встречи без подтверждённого слота; hh.ru и внешние каналы — только при реально доступной официальной интеграции. Не выдумывает работодателя, зарплату, условия или слоты.

### Создание HR-агента (минимум)

- **Название:** предлагаем «HR-рекрутер» (редактируемо, не prompt).
- **Вакансии:** выбери существующие или «Создам позже». Если вакансия уже содержит работодателя и условия, повторно не спрашивать.
- **Кто принимает HR-решения:** owner в personal автоматически; owner или разрешённый HR в team (проверка назначения до LIVE).
- **Каналы:** «Подключить позже» допустимо для черновика, но для LIVE выбранного способа интервью нужен рабочий канал; обязанность уведомления о данных — у конкретной формы/лендинга.
- Никаких полей «Как вести интервью», «Как отказать», «Как реагировать на неизвестное» или универсальных инструкций. «Создать» — не «Запустить».

### В карточке HR-агента

Внутреннее меню «Настройки»: **Вакансии**, **Ответственный и уведомления**, **Каналы и разрешения**, **Модель и лимиты**, **Доступы и теги**, **Перед запуском**. Опционально read-only «Что умеет HR-рекрутер» с понятным обзором встроенных функций, но без editable профессиональных правил.

**Настройки вакансии — отдельная форма:** роль, число мест, условия, обязанности, версии must-have/nice-to-have критериев, допустимые доказательства и вопросы, интервью, поля отклика и информирование об обработке данных, разрешённые мессенджеры, лендинг и HR owner. Изменения версии не должны задним числом переоценивать прежних кандидатов без контролируемой процедуры.

**Важно:** выбор вакансии для агента — связь; не создавать второй дублирующий редактор вакансии внутри настроек агента. Разные каналы и вопросы относятся к вакансии или её форме, а не ко всей профессии.

## Остальные пять профессий

| Профессия | Уже встроено | Только то, что задаёт пользователь |
|---|---|---|
| **Консультант** | Вежливый фактологический ответ, проверка источников, неизвестные и противоречия, уточнения, запрет выдуманных обещаний, штатный handoff | Темы и предмет консультаций (не «обучение консультировать»), актуальные FAQ/документы/каталог, канал, ответственный при неизвестном |
| **Менеджер заявок** | Выяснение потребности, минимальный сбор данных, типовая квалификация, валидация, обработка неполных данных, передача | Типы заявок, конструктор необходимых полей и условий, получатель заявки, опциональный CRM mapping, доступные каналы и источники |
| **Менеджер продаж** | Корректная работа с возражениями, выяснение потребности, честные предложения, запрет обещаний скидок/оплаты без подтверждения | Каталог и актуальные цены/условия, допустимый результат (предложение/лид/встреча), шаблон КП, подтверждённые скидки, CRM, ответственный |
| **Специалист поддержки** | Безопасная диагностика, триеж, проверки доступа, не запрашивает секреты, не обещает несуществующие сроки, безопасный handoff | Продукт, категории проблем, инструкции/playbooks, разрешённые инструменты, рабочие часы/SLA если есть, очередь оператора |
| **Агент мониторинга** | Безопасный polling, dedup, отделение старых событий от новых, фактические проверки, retry и антиспам | Что наблюдать, доступные источники, фильтры/пороги, частота/часовой пояс, куда уведомлять, опциональный digest |

Ни одна профессия не требует, чтобы пользователь формулировал собственный профессиональный системный prompt.

## Встроенный handoff без свободного поля

**Включены без переключателей:** запрос человека; недостаточно достоверных данных; существенные противоречия; действие требует согласования; операция недоступна/нет scope; критичные риски; сценарно обязательный финальный человеческий шаг (HR-решение). Каждая профессия добавляет свой набор автоматических триггеров. Handoff фиксирует полный контекст, причину и статус, избегает параллельных ответов после takeover.

**Пользователь выбирает только маршрут:** в personal — владелец; в team — сотрудник или разрешённая очередь/отдел; при необходимости допустимый канал уведомления и реальные часы работы. Если получатель недоступен, заявка остаётся в очереди, без обещания немедленного ответа. Не показывать обобщённое «Когда передавать человеку» — нельзя отключать обязательные триггеры текстом.

## Принцип готовности из коробки

Есть разница между **профессионально настроен** и **может безопасно работать на реальных данных**. Агент знает свою профессию с момента создания, но для LIVE сценария нужны предметные факты, разрешения, подключённый канал/источник, достижимый человек, действующая подписка и AI-кошелёк. Без этого агент остаётся редактируемым черновиком; он не должен выдумывать данные.

Показывать владельцу checklist только реально недостающих **привязок**; не требовать настройки профессионального поведения. Правила успешного запуска проверяет backend при commit, а не статическая форма.

## UX принцип

На создании 1–3 понятных поля по профессии, плюс «добавить позже» для необязательных зависимостей, с autosave. В подробной карточке — не гигантская форма, а конкретные объекты (вакансии, заявки, категории проблем, источники), связи и разрешения. Показывать объяснение «Агент уже умеет...» read-only при необходимости. Если у Workspace заполнены профиль, бренд, разрешённый HR, документы и интеграции, повторно не спрашивать.

## Реализация после согласования

1. Убрать UI поля `instructionInput`, `taskSpecificInput`, `handoffInput` и клиентские проверки `!instruction.trim() / !handoff.trim()`; **не удалять данные до миграции**.
2. Создать config schema per profession + ссылки на business objects; backend validation per enabled scenario.
3. HR: связать vacancy objects, HR recipient, permissions/notification settings; запрет автоотказа server-owned.
4. Общий controlled handoff engine c profession triggers and per-tenant routing.
5. Негативные тесты на prompt injection, ложные обещания, нет источника, нет HR, нет рабочего канала, double application, unavailable tool и запрет автоотказа.
6. Не менять утверждённые экран платформы «Обзор» и таблицу «Агенты»; дизайн детали обновить после согласования настоящих конфигурационных полей.

**Открытый вопрос для согласования только о UX:** показывать read-only блок «Что умеет агент» во вкладке «Обзор», в «Настройках» или только в подсказке при выборе профессии? На безопасность и доменную модель это не влияет.
